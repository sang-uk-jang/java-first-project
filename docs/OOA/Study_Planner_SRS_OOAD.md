## 1. 개요

### 1.1 목적
본 문서는 **Study Planner**의 기능 및 비기능 요구사항을 명확히 정의하여, 객체지향 분석·설계(OOAD), 구현, 테스트 과정에서 공통 기준으로 활용하는 것을 목적으로 한다.

### 1.2 프로젝트 배경
종이 플래너는 기록 수정·삭제가 번거롭고 과거 학습 내역을 검색하거나 장기 보관하기 어렵다. Study Planner는 날짜 기반으로 학습 기록을 관리하고 파일에 저장하여 이러한 불편을 줄이는 Java 애플리케이션이다.

### 1.3 범위
**포함 범위 (필수)**
1. 캘린더 표시
2. 날짜 선택
3. 스터디 기록 생성
4. 스터디 기록 조회 및 수정
5. 스터디 기록 삭제
6. 학습 기록 파일 저장 및 불러오기
7. 조건 검색

**제외 범위 (이번 버전)**
- 다중 사용자 계정 및 로그인
- 학습 타이머
- 클라우드 동기화 및 외부 DB 연동
- 알림 및 외부 캘린더 연동

> 본 명세서는 **단일 사용자, 로컬 실행 및 로컬 파일 저장**을 가정한다. GUI/CLI 방식과 실제 파일 형식은 설계 단계에서 확정한다. 아래 요구사항은 두 방식 모두 적용 가능하도록 기술한다.

### 1.4 용어
| 용어 | 정의 |
|---|---|
| 스터디 기록(StudyRecord) | 특정 날짜에 수행하거나 계획한 학습 내용을 나타내는 데이터 |
| 선택 날짜 | 사용자가 달력에서 고르거나 직접 지정한 유효한 날짜 |
| CRUD | Create(생성), Read(조회), Update(수정), Delete(삭제) |
| 영속화(Persistence) | 프로그램을 종료해도 데이터를 파일에 보존하는 것 |
| OOAD | 객체를 중심으로 요구사항을 분석하고 역할·책임·관계를 설계하는 방법론 |

## 2. 전체 시스템 설명

### 2.1 사용자와 운영 환경
- **주 사용자**: 본인의 학습 일정을 관리하는 단일 사용자 1명
- **운영 환경**: Java 실행 환경(JDK 버전은 팀에서 확정), 로컬 파일 읽기·쓰기 가능한 PC
- **데이터 저장**: 로컬 파일 기반

### 2.2 기본 업무 흐름
1. 프로그램 실행 및 저장된 학습 기록 불러오기
2. 캘린더 탐색 후 날짜 선택
3. 선택 날짜의 기록 조회 또는 생성
4. 필요한 경우 기록 수정·삭제
5. 조건 검색으로 기존 기록 탐색
6. 변경된 기록을 파일에 저장


## 3. 기능 요구사항 (Functional Requirements)

> **우선순위**: Must = 필수, Should = 권장. 모든 FR은 Must로 정의한다. 표의 **검증 기준**은 수용 테스트의 합격 조건이다.

### 3.1 FR-01 캘린더 기능
| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-01 |
| 이름 | 캘린더 표시 및 월 이동 |
| 우선순위 | Must |
| 사전 조건 | 프로그램 실행 중 |
| 입력 | 표시할 연도·월, 이전 달/다음 달 이동 요청 |
| 처리 | 해당 월의 날짜를 실제 달력 규칙(월별 일수, 윤년, 요일)에 맞게 구성 |
| 출력 | 현재 표시 연월과 날짜 목록(달력 형태) |
| 예외 | 지원 범위를 벗어난 연도·월은 안내 후 기존 화면 유지 또는 재입력 요청 |
| 검증 기준 | 임의의 연월에서 요일·날짜 배치가 정확하고 전월/익월로 이동할 수 있다. |

### 3.2 FR-02 날짜 선택 기능
| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-02 |
| 이름 | 날짜 선택 |
| 우선순위 | Must |
| 사전 조건 | 캘린더가 표시되었거나 날짜 입력 기능을 이용할 수 있음 |
| 입력 | 연·월·일 또는 캘린더의 날짜 |
| 처리 | 날짜 유효성 확인 후 선택 날짜 갱신 |
| 출력 | 선택 날짜 표시 및 해당 날짜의 기록 조회 기능 제공 |
| 예외 | 존재하지 않는 날짜(예: 2월 30일)는 거부하고 재선택 요청 |
| 검증 기준 | 정상 날짜를 선택하면 선택 값이 변경되며, 잘못된 날짜는 저장·적용되지 않는다. |

### 3.3 FR-03 스터디 기록 생성
| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-03 |
| 이름 | 스터디 기록 생성 |
| 우선순위 | Must |
| 사전 조건 | 유효한 날짜가 선택됨 |
| 입력 | 학습 제목(필수), 학습 내용(선택) |
| 처리 | 입력값 검증 → 고유 ID 생성 → 선택 날짜에 기록 추가 |
| 출력 | 등록 성공 메시지 및 갱신된 해당 날짜의 기록 목록 |
| 예외 | 제목이 공백인 경우 생성 거부, 오류 안내 |
| 검증 기준 | 유효한 입력으로 생성한 기록이 해당 날짜 조회 결과에 즉시 나타나며, 중복되지 않는 ID를 가진다. |

### 3.4 FR-04 스터디 기록 조회 및 수정
| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-04 |
| 이름 | 기록 조회 및 수정 |
| 우선순위 | Must |
| 사전 조건 | 조회 대상 날짜 또는 기록 ID가 지정됨 |
| 입력 | 조회 대상 날짜/기록 ID, 수정할 제목·내용·학습 날짜 |
| 처리 | 해당 기록 조회; 수정 요청 시 존재 여부 및 입력값 검증 후 변경 반영 |
| 출력 | 기록 정보(날짜, 제목, 내용, ID) 또는 수정 후 정보 |
| 예외 | 존재하지 않는 기록 ID, 잘못된 날짜, 공백 제목일 경우 수정 거부 |
| 검증 기준 | 지정 날짜의 기록을 모두 조회할 수 있고, 특정 기록 수정 후 재조회 시 변경 내용이 반영된다. |

| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-05 |
| 이름 | 기록 삭제 |
| 우선순위 | Must |
| 사전 조건 | 삭제 대상 기록이 존재함 |
| 입력 | 삭제할 기록 ID 및 사용자 확인 |
| 처리 | 삭제 대상을 확인한 후 해당 기록을 목록에서 제거 |
| 출력 | 삭제 결과 안내 및 갱신된 기록 목록 |
| 예외 | 존재하지 않는 ID나 삭제 취소 시 실제 데이터를 변경하지 않음 |
| 검증 기준 | 삭제 확인 후 조회 및 검색에서 해당 기록이 나타나지 않으며, 취소 시 유지된다. |

### 3.6 FR-06 학습 기록 저장 및 불러오기
| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-06 |
| 이름 | 로컬 파일 저장 및 불러오기 |
| 우선순위 | Must |
| 사전 조건 | 저장을 위한 파일 경로가 결정되어 있음 |
| 입력 | 현재 기록 데이터 또는 기존 저장 파일 |
| 처리 | 기록을 파일 형식으로 직렬화하여 저장; 파일을 읽어 기록 객체로 복원 |
| 출력 | 저장/불러오기 성공 여부 및 복원된 데이터 |
| 예외 | 파일 없음: 최초 실행 시 빈 목록으로 시작할 수 있음; 권한 오류·손상된 파일: 안내하고 정상 데이터의 임의 덮어쓰기를 방지 |
| 검증 기준 | 기록 생성·수정·삭제 후 저장하고 프로그램을 재실행해 불러오면 저장 당시의 기록 상태와 일치한다. |

**설계 시 결정 사항**: 파일 포맷, 자동 저장 여부 및 저장 시점, 기본 파일 경로, 저장 실패 시 복구 정책. 단, 저장과 불러오기는 반드시 제공한다.

| 항목 | 명세 |
|---|---|
| 요구사항 ID | FR-07 |
| 이름 | 학습 기록 조건 검색 |
| 우선순위 | Must |
| 사전 조건 | 프로그램 실행 중; 검색 대상 기록 목록에 접근 가능 |
| 입력 | 학습 제목 키워드 및/또는 날짜 범위 |
| 처리 | 검색 조건에 일치하는 기록 필터링; 조건 여러 개 입력 시 모두 만족하는 기록 반환(AND) |
| 출력 | 일치하는 기록 목록(날짜, 제목, ID 등)과 결과 없음 안내 |
| 예외 | 시작일이 종료일보다 늦거나 날짜 형식이 잘못된 경우 검색 거부 후 안내 |
| 검증 기준 | 키워드 단독, 날짜 범위 단독, 두 조건 동시 검색이 가능하고, 일치하는 항목만 반환한다. |

**검색 규칙 초안**: 제목에 대한 부분 문자열 검색, 날짜 범위의 양 끝 날짜 포함. 검색 규칙은 구현 전 팀 합의로 확정한다.

## 4. 비기능 요구사항 (Non-functional Requirements)

| ID | 분류 | 요구사항 및 검증 방법 |
|---|---|---|
| NFR-01 | 사용성 | 사용자는 주요 기능(조회, 생성, 수정, 삭제, 검색, 저장/불러오기)을 메뉴 또는 화면에서 식별하고 실행할 수 있어야 한다. 시연으로 확인한다. |
| NFR-02 | 정확성 | 날짜 계산은 윤년을 포함한 실제 달력 규칙을 준수한다. 경계 날짜 테스트로 확인한다. |
| NFR-03 | 데이터 무결성 | 잘못된 입력이나 저장 실패로 기존 정상 기록이 불필요하게 변경되지 않아야 한다. 오류 시나리오로 확인한다. |
| NFR-04 | 유지보수성 | UI, 도메인 모델, 기록 관리 로직, 파일 저장 로직의 책임을 분리하여 설계한다. 코드 리뷰로 확인한다. |
| NFR-05 | 구현 제약 | Java 객체지향 프로그래밍, Java Collections, 파일 입출력을 사용한다. 소스 코드에서 확인한다. |
| NFR-06 | 오류 처리 | 사용자가 입력값 오류·파일 오류의 원인을 이해할 수 있는 메시지를 제공하고, 가능한 경우 프로그램이 계속 동작해야 한다. 예외 테스트로 확인한다. |
| NFR-07 | 성능 | 단일 사용자의 일반적인 학습 기록 관리가 과도한 지연 없이 동작해야 한다. 구체적인 기록 수 및 최대 응답시간은 팀 테스트 환경을 정한 후 확정한다. |

## 5. OOAD 기반 객체지향 분석

### 5.1 액터(Actor)
- **사용자(User)**: 캘린더를 확인하고 학습 기록을 관리하는 단일 액터
- 로컬 파일 시스템은 외부 저장 자원이며, 사용자와 같은 의미의 주 액터는 아님

### 5.2 유스케이스 목록
| 유스케이스 ID | 유스케이스 | 관련 요구사항 | 주 액터 |
|---|---|---|---|
| UC-01 | 월별 캘린더 조회 및 이동 | FR-01 | 사용자 |
| UC-02 | 날짜 선택 | FR-02 | 사용자 |
| UC-03 | 학습 기록 등록 | FR-03 | 사용자 |
| UC-04 | 학습 기록 조회 | FR-04 | 사용자 |
| UC-05 | 학습 기록 수정 | FR-04 | 사용자 |
| UC-06 | 학습 기록 삭제 | FR-05 | 사용자 |
| UC-07 | 학습 기록 저장 | FR-06 | 사용자 |
| UC-08 | 학습 기록 불러오기 | FR-06 | 사용자 |
| UC-09 | 조건 검색 | FR-07 | 사용자 |

### 5.3 핵심 유스케이스 시나리오

**UC-03 학습 기록 등록**
1. 사용자가 날짜를 선택한다.
2. 시스템이 선택 날짜를 표시한다.
3. 사용자가 제목과 내용을 입력하고 등록을 요청한다.
4. 시스템이 제목과 날짜를 검증한다.
5. 시스템이 새 ID로 `StudyRecord`를 생성하고 저장 대상 목록에 추가한다.
6. 시스템이 등록 결과를 표시한다.

대안 흐름: 제목이 공백이면 생성하지 않고 입력 오류를 표시한다.

**UC-05 학습 기록 수정**
1. 사용자가 날짜별 목록에서 기존 기록을 선택한다.
2. 시스템이 기존 필드를 표시한다.
3. 사용자가 변경할 필드를 입력하고 수정을 요청한다.
4. 시스템이 입력값을 검증한다.
5. 시스템이 해당 ID의 기록만 갱신한다.
6. 시스템이 수정 결과를 표시한다.

대안 흐름: ID가 없거나 입력값이 유효하지 않으면 변경 없이 오류를 표시한다.

**UC-07/08 저장·불러오기**
1. 사용자가 저장을 요청한다.
2. 시스템이 기록 목록을 파일로 변환해 기록한다.
3. 시스템이 저장 성공 또는 실패를 알린다.
4. 프로그램 재실행 또는 불러오기 요청 시 저장 파일을 읽는다.
5. 시스템이 검증된 데이터로 객체와 기록 목록을 복원한다.

대안 흐름: 파일이 없으면 초기 상태로 진입하고, 파일이 손상되었으면 오류를 안내한다.

### 5.3 OOAD 설계 원칙 및 Java 적용
- **캡슐화**: `StudyRecord`의 필드는 `private`으로 선언하고 메서드로 유효한 상태 변경을 보장한다.
- **단일 책임**: 날짜 계산, 학습 기록 CRUD, 파일 저장, UI를 별도 클래스에 배치한다.
- **추상화·다형성**: `RecordRepository` 인터페이스를 사용하면 향후 파일 포맷이나 저장 방식 변경 시 도메인 로직 수정 범위를 줄일 수 있다.
- **Java Collections**: 기록 목록은 `List<StudyRecord>` 등으로 관리하고 필요 시 ID 검색용 `Map<String, StudyRecord>`를 활용한다.
- **표준 날짜 타입**: `java.time.LocalDate`, `YearMonth` 활용을 권장한다.
- **예외 처리**: 입력값 오류와 파일 입출력 오류를 구분해 처리한다.

## 7. 팀 합의 필요 사항 (미확정)

다음 항목은 기능 자체를 바꾸지 않지만 구현과 테스트 방식에 영향을 주므로 개발 착수 전에 확정한다.

1. **학습 기록 필드**: 현재 최소 필드는 `id`, `date`, `title`, `content`이며, 과목명·학습 시간·완료 여부 추가 여부
2. **검색 방식**: 제목 부분 일치 및 날짜 범위에 더해 내용·과목 검색을 허용할지 여부
3. **삭제 확인 방식**: 확인 단계의 UI 구현
4. **환경 및 품질 기준**: JDK 버전, OS 범위, 성능 테스트 데이터 규모·응답시간
